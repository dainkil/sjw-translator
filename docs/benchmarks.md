# 실측 벤치마크

모든 수치는 실측이며, 측정 방법·환경을 함께 기록한다. (계획서 원칙 4)

## NER: ONNX 변환 전후 비교 (M1, 2026-08-31)

- 환경: Apple M5, 16GB RAM, CPU 단건 추론 (배치 없음)
- 데이터: 골든셋 `eval/eval300_1925.json` 중 무작위 100문장 (seed=42)
- 재현: `cd ner-server && uv run python scripts/benchmark.py --n 100`

| 엔진 | mean | p50 | p95 | PyTorch 대비 엔티티 완전일치 | 골든셋 PER recall | 모델 크기 |
|---|---|---|---|---|---|---|
| PyTorch (기준) | 28.9ms | 17.9ms | 68.7ms | — | 102/102 (100%) | 709MB |
| ONNX fp32 | 16.1ms | 10.6ms | 65.4ms | 100/100 (100%) | 102/102 (100%) | 709MB |
| **ONNX INT8 (채택)** | **14.8ms** | **8.3ms** | **62.4ms** | 97/100 (97%) | **102/102 (100%)** | **178MB** |

**규칙 기반 축소판 대조 (M2.5-S3, 2026-09-01):** `RulePatternRecognizer`(정규식 3규칙: 以◯爲 제수 / 성씨+행위동사 / 관직+성명) — 동일 골든셋에서 **PER recall 26.9%, precision 62.0%** (tp=103 fp=63 fn=280, `RulePatternRecognizerTest` 회귀 하한 포함). ONNX recall 100%와의 이 격차가 "KB 주입 효과" A/B의 대조군이자 NER 장애 시 degrade 경로의 비용이다. 교체는 `NER_MODE=rule` 설정만으로 (수용 기준 2).

**해석**
- INT8 채택: p50 기준 2.2배 빠르고 메모리 4분의 1. 문장 단위 완전일치가 97%로 소폭 떨어지지만, 실제 파이프라인이 소비하는 신호(PER surface 검출)는 골든셋 recall 100%로 동일.
- 계획서 §2.1의 "NER 100~300ms (CPU)" 가정 대비 **한 자릿수 ms로 실측** — NER은 지연 예산에서 사실상 소거된다. GPU 배제(ADR-003)의 실측 근거가 이 표다.
- 주의: 서버 경유 시 HTTP 왕복이 추가된다. 파이프라인 관점 지연은 M1 완료 시 단계별 분해로 재측정.

## E2E 단계별 지연 분해 (M1, 2026-08-31)

- 경로: API(:8080) → NER 서버(:8100) → KB 링킹(in-memory) → 프롬프트 조립 → Gemini (무료 티어)

**내부 단계 (모델 무관, 실측):** NER 19~24ms(HTTP 왕복 포함; 서버 내 추론은 8.3ms), KB 링킹 ≤1ms, 프롬프트 조립 ≤1ms.

**LLM 단계 (모델별 실측):**

| 모델 | n | llm mean | llm p50 | llm p95 | **LLM 비중 (p95)** | 토큰 in/out (평균) |
|---|---|---|---|---|---|---|
| gemini-3.5-flash (T1 기본, thinking) | 17 | 12,112ms | 11,959ms | 18,812ms | **99.9%** | 820 / 115 |
| gemini-3.1-flash-lite (T0 후보) | 10 | 3,237ms | 2,988ms | 6,475ms | **99.7%** | 822 / 130 |

> **§2.1 확정: 전체 p95의 99.7~99.9%가 통제 밖 외부 LLM이다.** 계획서의 "90% 이상" 가설이 상회 확정됐다.
> 내부 최적화(NER GPU 등)의 ROI가 0에 수렴한다는 D3 결정의 최종 근거.

**부수 관찰 (무료 티어 운영 현실, ADR-016):**
- `gemini-3.5-flash` 일일 무료 한도 **RPD 20 실측** (429 응답의 `quotaValue:"20"`, `PerDayPerProjectPerModel`). 30문장 측정 중 13건이 이 한도로 차단됨 → n=17.
- quota가 **모델별로 독립**이므로 티어 라우팅(M4)이 곧 일일 quota 풀링이 된다.
- `gemma-4-26b-a4b-it`는 혼잡 시간대에 짧은 프롬프트도 16초+, 전체 프롬프트는 60초 타임아웃 — 무료 엔드포인트의 시간대별 변동성이 크다. 배치 워크호스 선정은 M2에서 RPD·안정성 실측 후 결정.
- 요청당 입력 ~820tok = 페르소나 448 + Structured Output 지시문·KB블록 ~250 + 원문 ~120. 오버헤드 비중 85%.

동일 인물(領議政李元翼)을 포함해도 문장에 따라 전 토큰 O 예측이 나온다 (예: `...進曰臣以老病...勉留之` 45자 문장 — PyTorch 원본도 동일). silver-label 학습의 문맥 민감성으로, 서빙 결함이 아님 (INT8은 원본을 충실 미러링). **시사점: "엔티티 0개 = 쉬운 정형문"이 아니므로 M4의 T0 판정은 NER 결과 단독이 아니라 정형문 패턴 매칭과 결합해야 한다.**

## 배치 처리량 (M2, 2026-09-01)

- 경로: 배치 발행(BatchPump, 윈도우 3) → Redis Streams → 워커 → 적응형 rate 버킷 → `gemini-3.1-flash-lite`
- 조건: 골든셋 30문장 배치 × 2회, `SJW_RATE_INITIAL_RPM=60` (버킷 상한을 provider보다 높게 두고 실제 한계를 관찰)
- 재현: `N=30 OFFSET=110 ./deploy/demo-rate-control.sh` / 수치는 `cost_ledger`의 첫·끝 기록 시각 기준

| 구성 | 완료 | 실패 | LLM 호출 (원장) | 소요 | 처리량 |
|---|---|---|---|---|---|
| 워커 1대 | 30/30 | 0 | **정확히 30회** | 77s | **23.4 jobs/min** |
| 워커 2대 (버킷 공유) | 30/30 | 0 | **정확히 30회** | 78s | **23.1 jobs/min** |

**해석**
- **워커를 2배로 늘려도 처리량이 늘지 않는다 (23.4 → 23.1).** 병목이 워커 CPU가 아니라 외부 API 왕복이라는 D11(워커 단일 인스턴스 확정)의 실측 근거.
- 두 배치 모두 원장 기준 호출 수 = job 수 — 2워커 경합 상황에서도 **중복 호출 0건** (멱등 키 + 버킷 공유 동작 확인).
- 2워커 실험은 `SJW_RATE_MAX_WAIT_MS=20000` 오버라이드가 필요했다. 기본값(120s)이 stale claim 회수 주기(30s)보다 길어, 정상 대기 중인 워커의 메시지를 다른 워커가 회수해 중복 호출할 수 있기 때문 — 이 제약 자체가 D11의 두 번째 근거다.

## 적응형 rate control 검증 (M2, 2026-09-01)

수용 기준 "429 유발 시 rate 자동 하향, 회복 후 상향"의 증거 상태:

- **라이브로 확인된 것:** Redis Lua 토큰 버킷이 워커 2대를 단일 rate로 페이싱 (데모 타임라인의 `tokens`/`streak` 텔레메트리), 연속 성공 카운팅, 60 RPM 상한에서 30/30 완료.
- **라이브로 유발하지 못한 것:** 실제 429. 버킷 상한 60 RPM·워커 2대에서도 flash-lite의 유효 한도에 도달하지 않았다 (2회 시도 모두 429 0건). AIMD 하향(429→rate 절반)·상향(연속 5성공→+1 RPM)은 **실측 429 응답 원문을 사용한 리미터 단위 테스트**로 검증되어 있다.
- 더 강한 유발 수단(워커 3대+, RPM 추가 상향)은 D11 위배·quota 소진이라 시도하지 않는다. **강제 429 하의 라이브 검증은 M6 mock provider 부하 테스트로 이관** (계획서 §10 M6: "워커 다중화는 mock provider 하에서만 검증").

## 품질 게이트 (M2.5-S5, 2026-09-01)

**게이트 오탐률 (전문가 번역 대상, LLM 호출 0회):** 골든셋에서 링크 확정 인명을 보유한 181문장의
전문가 번역을 게이트에 통과시켜 REJECTED 비율을 측정 — 정답에 대한 REJECTED = 오탐.

| 게이트 버전 | 오탐 | 오탐률 |
|---|---|---|
| 전체 이름 일치만 | 9/181 | 5.0% |
| **+ 이형 표기 보정 (성 생략 허용, 채택)** | **7/181** | **3.9%** |

잔여 오탐: 1자 표층형(珙→윤공, 翼→조익, 衛→안위)과 음차 변형(沈諿 집/즙) — 인명별 허용 목록 후보.
이 수치가 티어 승격(T1 quota 소모)의 낭비율 상한이다. 재현: `QualityGateGoldensetTest` (회귀 상한 0.15 고정).

**오프라인 기준선 (`eval/score_db.py`, 시스템 결과 n=70, gemini-3.1-flash-lite):**
chrF **41.52**, 링크 확정 인명 반영률 **99.09%** (110건 중 109). 비열등 임계: chrF −2.0 이내, 반영률 하락 0.

**인명 지표 분리 (M3.5-S1, 2026-09-21, LLM 호출 0회).** 위 99.09%는 시스템이 KB로 확정해 **프롬프트에 주입한**
한글명이 번역문에 있는 비율이다 — 주입 소스와 채점 소스가 같으므로 순환 지표이고(선행 연구 보고서 §0 "닫힌
고리"), 번역 정확도가 아니라 지시 이행률이다. 캐시·라우팅 비열등 게이트로는 옳지만 품질 헤드라인으로는 쓰지
않는다. 같은 결과 n=70을 **독립 정답지**(`eval/ner_groundtruth_300.json` — 국편 사이트 `idx_person` 어노테이션,
SillokBERT·KB와 무관, KB MISS 인명도 분모에 포함)로 다시 채점한 값:

| 지표 | 값 | 분모 | 성격 |
|---|---|---|---|
| 주입 인명 반영률 | 99.09% (109/110) | 시스템이 확정·주입한 인명 | 게이트 지표 (순환) |
| **ETS** (엄격: 전체형 포함) | **98.21%** (110/112) | 정답지 인명, 문장 50 | **품질 지표** |
| ETS (관대: 성 생략 허용, 게이트 규칙) | 99.11% | 동일 | 참고 |
| ETS macro (문장별 평균, score_300.py 집계) | 97.33% | 동일 | 참고 |
| 전문가 번역 자체의 ETS (엄격 / 관대) | 97.13% / 97.91% (383건, 문장 187) | 골든셋 300 전체 | 상한 — 정답지 표기와 번역가 표기(성 생략·이칭)의 차이 |

정답지의 독립성은 "어느 한자 구간이 인명인가"에 있다. 한글 표기는 말모이 인물 정본을 공유하므로(연구 §1.3)
KB가 확정한 인명의 ETS 적중은 반영률과 거의 같이 움직이고, ETS가 추가로 잡는 것은 **시스템이 놓친·못
확정한 인명**이다. 이 n=70에서는 정답지 인명 112 대 주입 인명 110으로 둘이 거의 겹쳤다 — 골든셋의 KB
커버리지가 전수(MISS 36.51%)보다 훨씬 높다는 뜻이며, MISS 문장군에서의 ETS는 별도 측정 대상이다.
허용 하락폭은 M3.5-S2의 대조군 3라운드 폭으로 변형 채점 전에 고정한다(사후 임계 금지). 재현:
`uv run --with sacrebleu --with "psycopg[binary]" python eval/score_db.py` /
`... --self-check-reference` / `... --batch-id <uuid> --json --no-gate`.

## L2 템플릿 슬롯 캐시 (M3-S3, 2026-09-11)

라이브 전 스택(compose 5컨테이너), 모델 `gemini-3.1-flash-lite`.
문장은 실제 정형문 `以{인물}爲承旨`의 **인물만 바꾼 쌍** — 셋 다 인조 연간 KB 단일 후보이고
라이브 NER이 PER로 검출한다(score 0.99). 유황은 받침이 있고 김류는 없어 조사 보정이 드러난다.

| 항목 | 실측 |
|---|---|
| 슬롯화된 원문 (L2 키의 재료) | `以⟪PER1⟫爲承旨` → `template_hash=791d1c2896c4…` |
| 적재된 번역 템플릿 | `⟪PER1⟫을 승지로 제수하였다.` (slots=1, 생산 모델 `gemini-3.1-flash-lite`) |
| **히트 결과 (인물만 다른 문장)** | `以金瑬爲承旨` → **`김류를 승지로 제수하였다.`** — 조사가 `을`→`를`로 보정됨 |
| **job 2건에 대한 `cost_ledger` 행** | **1건** — 두 번째 문장은 LLM 호출 0회 |
| 히트 시 `tokens_in/out` | NULL |
| 히트 등급 | **DEGRADED** (ADR-009 — LLM이 생성한 문장이 아니다) |
| 카운터 | `translation.cache.hit{level=L2}`=1 |

**L1과의 결정적 차이: L2 히트는 NER 추론을 건너뛰지 못한다.** 슬롯화에 링크 확정 PER이 필요해
조회가 전처리 뒤에 오기 때문이다. 단계별 실측 (L2 히트 5건 누적, 첫 건은 콜드):

| 단계 | 평균 | 최대 |
|---|---|---|
| ner | 31.0ms | 86ms (콜드 1건 포함, 워밍 후 ≈17ms) |
| link | 0.0ms | 0ms |
| prompt | 6.0ms | 25ms |
| cache (L2 조회+재주입+게이트) | **4.8ms** | 7ms |
| **합계** | **≈42ms** (워밍 후 ≈23ms) | — |
| 비교: 미스 경로 (LLM 호출) | **2,450ms** (llm 2,398ms) | 2,953ms |

L1 히트(0~12ms)보다 느리고 미스(2,450ms)보다 100배 빠르다 — 이 순서가 2단 캐시를 둔 이유다.

**재주입 실패 → fallback (M3 수용 기준).** 적재된 템플릿에서 마커를 지우는 고장을 주입했다.

| 항목 | 실측 |
|---|---|

## L2 비열등 판정 (M3-S5, 2026-09-11)

L2 히트는 **LLM이 생성하지 않은 문장**이다 — 다른 문장의 번역 틀에 인명을 꽂아 만든다. 품질 증거
없이 서빙할 수 없으므로(ADR-009 배경 3) 같은 문장을 두 경로로 번역해 대조했다.

**생산 코드 경로로 측정했다.** L2 결과는 채점 스크립트가 아니라 실행 중인 api의
`TranslationCache.lookupL2` + `TemplateSlotter.reinject` + `QualityGate`가 만들고,
`meta.cacheHit == "L2_TEMPLATE"`로 확인한 건만 표본에 넣었다 (이식으로 근사하지 않았다).

```
① F(틀 적재 문장)을 LLM 번역 → 게이트 → 템플릿화 → 적재      [LLM 1회]
② R(히트 문장) 요청 → L2 히트 = 평가 대상                     [LLM 0회]
③ 템플릿 삭제 후 R 재요청 → LLM 직접 번역 = 대조군            [LLM 1회]
   → 양쪽을 R의 전문가 번역에 대해 chrF·확정 인명 재현율로 비교
```

표본 풀: S4 시뮬레이션의 L2 히트 1,392쌍 중 **정렬 검증 통과 1,220쌍**
(`simulate_cache.py --dump-l2-pairs`). 정렬 결함 172쌍은 reference를 정답으로 쓸 수 없어 제외했다.
층화: 패턴(positive-patterns.tsv 9종 + 없음) × 길이 3구간 → 실제 7개 층.

### 판정 결과 — **통과**

2회 독립 실행. 1차는 페이싱 없이(표본이 RPM 429로 깎여 n<60), 2차는 페이싱 4.5s + 429 재시도 + 과표본 ×1.25.

| 실행 | 라운드 | n | chrF (L2 / 대조군) | **chrF 차이** | 확정 인명 재현율 (L2 / 대조군) |
|---|---|---|---|---|---|
| 1차 | R1 | 53 | 36.23 / 38.43 | **−2.20** | 1.0000 / 1.0000 |
| 1차 | R2 | 53 | 38.22 / 39.19 | −0.97 | 1.0000 / 1.0000 |
| 1차 | R3 | 54 | 37.68 / 38.96 | −1.28 | 1.0000 / 1.0000 |
| 2차 | R1 | **60** | 36.56 / 38.02 | −1.47 | 1.0000 / 1.0000 |
| 2차 | R2 | 47 | 42.52 / 41.82 | +0.70 | 1.0000 / 1.0000 |
| 2차 | R3 | **60** | 38.18 / 38.14 | +0.04 | 1.0000 / 1.0000 |

| 지표 | 임계 (§5.4) | 실측 중앙값 | 판정 |
|---|---|---|---|
| chrF | −2.0 이내 | **1차 −1.28 / 2차 +0.04** (6라운드 전체 −1.13) | ✅ |
| 확정 인명 재현율 | **하락 0** (동등 요구) | **+0.0000** (6라운드 전부) | ✅ |

`uv run --with sacrebleu python eval/score_l2.py --pairs <dump>` — 종료 코드 계약은 `score_db.py`와 동일(위반=1).

**§5.4의 "3회 반복 중앙값"이 실제로 일했다.** 1차 R1은 **−2.20으로 임계를 넘었다** — 단일 측정이면
"위반"이 나왔을 것이다. 6라운드 범위가 −2.20 ~ +0.70으로 LLM 비결정성이 chrF 3포인트 폭을 만든다.
사전에 중앙값을 규정해 둔 것이 사후 해석 여지를 없앴다.

**확정 인명 재현율은 6라운드 전부 양쪽 1.0000이다.** 재주입이 확정 한글명을 직접 꽂으므로 구조적으로
보장되고, 조사 보정도 이름 자체를 훼손하지 않았다 — L2가 인명 정확도를 깎지 않는다는 것이
§5.4가 동등을 요구한 지표에서 확인됐다.

**표본에서 빠진 것:** `L2 미개입(적재 불성립)` 1~3건/라운드 — F가 VERIFIED가 아니었거나 확정 한글명
전체형이 번역문에 없어 템플릿화가 성립하지 않은 쌍이다(ADR-009 보수적 적재의 정상 동작).
2차 R2의 28건은 provider 일일 quota 소진(아래).

### 판정이 통과했지만 L2는 off로 유지한다

**품질 축은 통과했고, 결정을 가른 것은 수혜 크기다.** L2가 사는 것은 전수 기준 LLM 호출 1,075회
(+1.74%p)이고, 완역 환산으로는 캐시 17.4% 기준 **5.72년 → 5.63년**(약 5주)이다. 그 대가는
DEGRADED 등급 1,392건(LLM이 쓰지 않은 문장의 서빙), L1 히트 317건 잠식, 재주입 실패 표면의
유지 비용이다. 근거와 결정 기록은 ADR-009 "운영 상태".

### 부수 실측: `gemini-3.1-flash-lite`의 무료 티어 quota

판정 중 429가 42건 발생했고, **응답 본문의 `quotaValue`가 한도를 직접 알려줬다**
(3.5-flash RPD 20을 확정한 것과 같은 방법 — M1 §무료 티어).

| quotaId | quotaValue | 발생 |
|---|---|---|
| `GenerateRequestsPerMinutePerProjectPerModel-FreeTier` | **15** | 14건 (1차, 페이싱 없이 지속 ~17 req/min) |
| `GenerateRequestsPerDayPerProjectPerModel-FreeTier` | **500** | 28건 (2차 R2, 당일 누적 ~700 호출 후) |

`quotaDimensions.model` = `gemini-3.1-flash-lite` (42건 전부). **이것이 M2에서 유발에 실패했던
라이브 429다** — 종전에는 "60 RPM·2워커에서도 429 0건"이라 M6 mock provider에 이관해 뒀다.

**미해소 모순:** M2가 측정한 배치 처리량 **23 jobs/min**은 지금 확정된 **RPM 15**를 넘는데 그때는
429가 0건이었다. 가능한 설명은 ① 그 사이 quota 변경 ② 분당 창의 버스트 허용 ③ M2 측정 창이
1분 미만 — 셋 다 확증되지 않았다. M6에서 재측정 대상이다. **AIMD의 `initial-rpm: 20`·`max-rpm: 60`도
실측 15를 넘으므로 M4에서 재조정 후보다**(AIMD가 429로 스스로 내려오지만, 시작점이 한도 위면
매 기동마다 429를 한 번 사서 배운다).

### 부수 발견: 동기 경로에는 rate limiter·재시도·실패 분류가 없다

429 42건 전부가 클라이언트에 **HTTP 500**으로 나갔다. 워커는 `AdaptiveRateLimiter`(ADR-017) +
Resilience4j Retry/CircuitBreaker + `FailureClassifier` 9종을 갖고 있는데, 동기 경로(`/sync`,
`/stream`)는 Translator를 직접 호출한다. 그래서 provider quota 문제가 서버 내부 오류로 보인다.
측정 도구가 그 몫을 대신 졌다(페이싱 4.5s + 429 백오프 재시도) — 본래 서버가 할 일이다.
선례·처리 방향: `docs/troubleshooting.md` §6.

## 캐시 히트율 + 캐시 on/off 비용 비교 (M3-S4, 2026-09-11)

**LLM 호출 0회로 측정했다.** 히트율은 코퍼스·NER·KB가 정하는 성질이고 번역 LLM과 무관하다 —
캐시 키가 원문 해시와 슬롯화된 원문 해시로만 만들어지기 때문이다(ADR-009). 무료 티어(RPD 20)로
6만 문장을 실제 번역하는 것은 불가능하므로 이것이 유일하게 가능한 측정 경로다.

방법: **순차 재생.** 코퍼스를 문서 순서대로 훑으며 생산 코드와 같은 순서로 판정한다
(L1 조회 → L2 조회 → 미스면 LLM 1회 + 적재 정책대로 저장). 첫 등장은 항상 미스이므로 단순 중복
개수보다 낮게 나온다 — 워밍업이 반영된 수치다. 재현: `python3 eval/simulate_cache.py --years all`.

**이식 충실도.** 시뮬레이터는 `TextHash`·`FileKnowledgeSource.link`·`TemplateSlotter`·`QualityGate`의
Python 이식이다. 두 방향으로 검증했다: ① 생산 DB의 job 행과 대조 — `normalized_hash` 96건,
`template_hash` 9건 **전부 일치**(`--self-check`, 불일치 시 exit 1) ② 골든셋 게이트 오탐률
**3.9%를 정확히 재현**(7/181 — Java `QualityGateGoldensetTest`의 실측값과 동일).

### 결과

| | **A01 (인조 1년치)** | **인조 전수 23년치** |
|---|---|---|
| 문장 수 | 1,911 (2,000자 초과 2건 제외) | 62,056 (420건 제외) |
| L2 대상 문장 (링크 확정 PER ≥1) | 1,011 (52.9%) | 32,218 (51.9%) |
| **L1 구조적 반복** | 341 / 1,911 = **17.84%** | 9,712 / 62,056 = **15.65%** |
| **L2 구조적 반복** | 14 / 1,011 = 1.38% (전체 0.73%) | 1,717 / 32,218 = 5.33% (전체 **2.77%**) |
| 실효 히트율 — L1만 | 17.84% | 15.62% |
| **실효 히트율 — L1+L2** | **18.21%** | **17.36%** |
| L2의 순 기여 | +0.37%p | **+1.74%p** |

L2 기여가 1년치에서 0.37%p, 23년치에서 1.74%p다 — **틀 충돌은 코퍼스가 커질수록 늘어난다.**
1년치만 보고 L2를 판단하면 과소평가한다.

### 캐시 on/off 비용 비교 (Flash 공시가 counterfactual, 호출당 in 820 / out 266 tok)

인조 전수 62,056문장 기준:

| 구성 | LLM 호출 | L1 히트 | L2 히트 | 비용 | 문장당 |
|---|---|---|---|---|---|
| 캐시 off | 62,056 | 0 | 0 | 79,146원 | 1.28원 |
| L1만 | 52,360 | 9,696 | 0 | 66,780원 | 1.08원 |
| **L1+L2** | **51,285** | 9,379 | 1,392 | **65,409원** | 1.05원 |

**L2가 L1 히트를 일부 잡아먹는다** (9,696 → 9,379, −317). L2 히트는 L1으로 승격 적재하지 않으므로
(ADR-009 구현 메모 3) 그 문장의 이후 완전 일치 재요청이 L1을 비켜간다. 순효과는 +1,075 호출 절감 —
**"L2를 끄면 즉시 멈춘다"는 스위치 보장의 측정된 대가가 317회 호출(전체의 0.51%)이다.** 값싼 보험.

### 히트율은 배치 규모에 종속된다

캐시는 "이미 본 문장"만 맞춘다. 잔여 코퍼스(약 120만 문장)로 외삽하려면 방향을 알아야 한다:

| 문장 수 (문서 순서 누적) | L1 반복 | L2 반복 (전체 중) |
|---|---|---|
| 5,000 | 12.48% | 2.46% |
| 10,000 | 13.96% | 2.69% |
| 20,000 | 14.51% | 3.04% |
| 40,000 | 15.20% | 3.12% |
| 62,056 | **15.65%** | 2.77% |

**L1은 규모와 함께 단조 증가하며 6.2만 문장에서도 아직 상승 중이다** → 15.65%는 잔여 코퍼스에 대한
보수적 하한이다. L2는 3% 근처에서 평탄해진다. (1천~2천 구간이 18%까지 튀는 것은 누적 시작점이 A01
한 해이고 **같은 해 안의 반복이 해를 넘는 반복보다 촘촘**하기 때문이다 — A01 단독 17.84%가 전수
15.65%보다 높은 것도 같은 이유다.)

### 슬롯 범위를 넓히면 — ADR-009가 배제한 설계의 기회 크기

L2가 낮은 직접 원인은 **확정 PER만 슬롯화**하기 때문이다(ADR-009 v1). 관직·지명이 다르면 틀이 갈린다.
배제된 확장의 상한을 재두었다 (역어 정본이 없어 **실현 불가**, 달성 가능한 히트율이 아니다):

| 슬롯 범위 | 반복 틀 (전수) | 대상 중 | 전체 중 |
|---|---|---|---|
| PER만 (현행 v1) | 1,717 / 32,218 | 5.33% | **2.77%** |
| PER + LOC | 8,602 / 44,438 | 19.36% | **13.86%** |
| PER + LOC + 관직(KB 사전) | 9,701 / 50,057 | 19.38% | **15.63%** |

**기회는 관직이 아니라 지명(LOC)에 있다** — LOC를 더하면 2.77% → 13.86%(5배)인데, 관직을 더 얹어도
+1.8%p뿐이다. ADR-009의 재검토 조건은 "관직 역어 사전이 생기면 POS 슬롯화 재평가"였는데, 측정은
우선순위가 반대임을 보여준다. 조건을 개정했다(ADR-009).

**부수 발견: NER 모델에 POS(관직) 클래스가 없다.** 라벨은 `PER / LOC / DAT / POH`뿐이다
(전수 검출: PER 119,895 / LOC 33,469 / DAT 84 / POH 5). 계획서 §5.2의 "NER로 인명/날짜/관직 추출"과
슬롯 예시 `命{PER}爲{POS}`는 모델 능력과 불일치한다. 위 표의 관직 행은 NER이 아니라 **KB
`관직_리스트`의 한자 표기를 사전으로 마스킹**해 측정했다.

### 부수 발견: 원천 병렬 코퍼스의 원문↔번역 정렬 결함

A01의 게이트 REJECTED가 26.6%로 골든셋 실측(3.9%)과 크게 어긋나 실물을 확인한 결과,
`malmoi/Merged_Corpus_Final.json`의 짝이 **한 행씩 밀린 경우**가 있었다. 예:

```
원문 : ○ 大司諫朴東善啓曰, 積年罪戾之餘, …
번역 : 정언 오숙이 아뢰기를, "10여 년을 구차하게 목숨을 보전하다가 …   ← 다음 행의 번역
```

검출 방법: 확정 인명이 자기 번역에는 없는데 **이웃 행(±2) 번역에는 전부 있으면** 밀린 짝이다.

| 슬라이스 | 밀림 판정 (확정 PER 보유 문장 중) | 밀림 제외 후 게이트 오탐률 |
|---|---|---|
| A01 | 209 / 1,011 = 20.67% | 5.93% |
| 전수 | 3,620 / 32,218 = 11.24% | **4.36%** (골든셋 3.9%와 일치) |

보정 후 오탐률이 골든셋 실측과 맞는다 — **이식이 아니라 데이터의 결함**임이 확인된다.
히트율의 키 계산은 원문만 쓰므로 영향이 없고(전수 실효 히트율 17.34% → 17.36%), 영향은 적재 판정
쪽뿐이다. 런타임 품질 게이트가 의도 밖으로 **학습·평가 코퍼스의 정합성 검사기**로 동작한 사례다.
선례는 `docs/troubleshooting.md`.

### 측정의 경계

- 등급 판정은 **전문가 번역을 프록시로** 쓴다 (시스템 LLM 출력이 아니다). 게이트 오탐률 3.9%를
  같은 프록시로 측정한 M2.5-S5와 방법론이 일치한다. **키 중복으로 결정되는 구조적 히트율은 프록시와
  무관하게 정확하고**, 적재 정책을 반영한 실효 히트율만 프록시에 의존한다.
- 측정 대상은 **이미 국역된** 인조 연간이다(참조 번역이 있는 유일한 구간). 잔여 미번역분에 같은
  반복 구조를 가정하는 것은 외삽이다.
- 2,000자 초과 420건은 API 상한(`TranslateRequest @Size(max=2000)`)으로 제외했다. 실제 운영에서는
  분할 입력이 필요하고, 분할이 히트율에 미치는 영향은 미측정이다.



## 서빙 프롬프트 ablation (M3.5-S2, 2026-09-21~24 — 완료, **v4 채택**)

**왜.** 입력 토큰의 85%가 프롬프트다(`docs/cost-model.md`). 선행 연구는 역할 지정·번역 원칙이 효과 없고
예시 10·20개가 5개보다 낫지 않다고 했는데, 서빙 프롬프트는 페르소나 + [번역 원칙] + [문체표] + 예시 7개를
싣고 골든셋으로 ablation된 적이 없다. 준비 중 발견: **정답 코퍼스 300문장은 전부 `아뢰기를,“…”하니,`**(curly
따옴표, 공백 없음)인데 서빙 예시는 `아뢰기를, "…" 하니,`다 — chrF가 따옴표 문장마다 깎인다. 연구의 5예시는
코퍼스 관행과 일치한다. 그래서 구두점만 바꾼 v5를 변형에 넣었다.

  인명은 양쪽 동일(빠지거나 살아난 정답지 인명 없음). 한 쌍의 관찰이므로 3라운드 중앙값 판정과 별개의 해석 자료다.
- **v5 (구두점만, 라운드 1/3 — 중간):** chrF **39.62**, v0의 세 라운드(37.60~38.29)보다 위, 인명 지표·등급 동일,
  tokens_in 912.9(curly 따옴표가 5토큰 싸다). 예시 7개의 따옴표 표기를 코퍼스 관행으로 맞춘 것만으로 chrF
  +1.7 — 라운드 1 하나라 중앙값은 아직 없지만 v0 폭(0.69) 밖이다. 라운드 2는 16/60에서 일일 quota로
  QUOTA_PAUSED(오늘 사용 481회).

**부수: REJECTED의 첫 라이브 자연 발생.** 1차 시도(승격 on)에서 job `f2a59aa5` REJECTED(누락 兪榥→유황)
→ `gemini-3.5-flash` 승격 재호출 → VERIFIED. presentation §9 ⑨("아직 미관측") 항목이 닫혔다. 대가로 배치
예산 60이 59건에서 소진(BUDGET_EXHAUSTED)돼 그 배치는 폐기했고(모델 혼합), 승격 off·예산 2n으로
재실행했다. 승격을 끈 뒤에도 같은 문장이 v0·v1 모든 라운드에서 REJECTED — 프롬프트가 아니라 榥의 독음 문제다.
승격 경로가 실제로 작동한다는 것과, 그 비용이 3.5-flash quota 1회라는 것이 함께 실측됐다.

**최종 판정 (2026-09-24, `--verdict`).** 여섯 변형 모두 사전 고정 임계를 통과했다. 사전 등록 규칙(통과 변형 중
tokens_in 중앙값 최소)은 **v2**(문체표 제거, −13.6%, 품질 v0와 동일)를 고른다 — 판정 파일에 그대로 남긴다.

**채택은 v4(최소)** — 사용자 결정, 규칙과 다른 선택이며 이유를 여기와 ADR-013에 적는다:
- v4는 **품질 세 지표가 모두 오른 유일한 저토큰 변형**이다: chrF **+2.42**(40.14~40.45, v0 최고 38.29와 겹치지 않음),
  반영률 1.0000·ETS 0.9808(정답지 인명 +1 — v0~v2·v5에서 매 라운드 REJECTED이던 兪榥→유황이 살아남음), REJECTED 0.
- 대가는 v2 대비 **+22 tok(+2.8%)**. 규칙은 "품질이 같다면 싼 것"을 전제로 썼는데, 측정은 품질이 같지 않다는 것을
  보였다 — 규칙이 상정하지 않은 경우다. 규칙을 사후에 고치지 않고, 규칙의 선택(v2)과 실제 채택(v4)을 둘 다 기록한다.
- v3(연구 REP 5예시 + 원칙 유지)도 인명은 v4와 같지만 +14.6% 토큰 — v4와의 차이는 원칙·문체표이고, 그것들은
  값을 하지 않는다(v4가 v3보다 chrF도 높다).

**이 실험이 보인 것.**
- 품질을 움직인 것은 **예시의 표기**다: v5(구두점만) +1.92, v3·v4(코퍼스 관행 예시 5개) +1.82·+2.42. 페르소나·원칙
  (v1 −1.48)은 짧은 정형문의 앵커였지만, 코퍼스 관행 예시가 그 역할을 더 잘 한다.
- 문체표(v2)는 토큰만 먹고 품질에 기여하지 않았다.
- 인명(ETS)은 어느 변형에서도 떨어지지 않았다 — 인명을 지키는 것은 프롬프트 문구가 아니라 KB 주입이다
  (아래 KB 주입 A/B: 주입을 끄면 0.9038).

## 가짜 LLM provider — 429·승격 유발 (M6 선행, 2026-09-21)

**무엇.** `Translator` 포트의 두 번째 provider `fake`(`FakeProvider`/`FakeTranslator`, ADR-018 개정). 네트워크 0,
quota 0. LLM을 흉내 내지 않고 파이프라인이 LLM에 기대는 **계약만** 지킨다 — 프롬프트의 [등장 인물 한자→한글]
블록을 읽어 원문의 표면형을 한글명으로 치환한 문자열을 Structured Output JSON으로 돌려주고, usage를 동반하며,
`FAKE_RPM`/`FAKE_RPD`/`FAKE_ERROR_RATE`/`FAKE_DROP_NAME_RATE`로 429(실측 로그 형식의 본문)·503·확정 인명 누락을
원하는 비율로 유발한다. 어느 어댑터인지는 레지스트리 항목의 `provider`가 정하고(모르는 값은 기동 실패), 가짜 결과는
**캐시에 적재하지 않는다**(키에 모델이 없다). 채점기는 `fake-*` 결과를 기본 제외한다(`--include-fake`).

**왜.** M2 수용 기준 ②(429 → 하향 → 상향)를 60 RPM × 2워커로도 라이브 유발하지 못해 "M6 mock"으로 이관했었다.
부하 테스트·CI E2E도 무료 quota를 태울 수 없다. 실측을 대체하는 것이 아니라 **실측이 불가능한 조건을 만드는** 장치다.

**라이브 (compose 스택, `deploy/demo-fake-provider.sh A|B|C`, 골든셋 층화 60문장, 워커 캐시 off):**

| 시나리오 | 조건 | 결과 | 실 모델 원장 증가 | 캐시 키 증가 |
|---|---|---|---|---|
| A 완주 | latency 100ms | 60/60 COMPLETED **120s**, VERIFIED 38 / DEGRADED 22 (실 모델 실행과 같은 22 — KB 미등재 문장군), 원장 60행 비용 0 | **0** | **0** |
| B 429 유발 | `FAKE_RPM=20` | 60/60 완주 224s. 미실측 모델이라 리미터가 20에서 출발해 39까지 상향 → 가짜 한도에 걸려 **429 → `rate 39 → 19 RPM, 쿨다운 35,600ms (provider 힌트)`**, 다시 **`23 → 11 RPM, 쿨다운 1,800ms`** — 429 본문의 "retry in Ns"를 `RetryAfterHint`가 읽어 쿨다운으로 썼다 | 0 | 0 |
| C REJECTED→승격 | `FAKE_DROP_NAME_RATE=0.3 FAKE_SEED=42`, 승격 on → `fake-flash` | **REJECTED 7건 → 승격 재호출 7회**: VERIFIED 4 / DEGRADED 2 / 재REJECTED 1(승격 모델도 30%로 빠뜨림). 원장 lite 60 + flash 7 = 67행, 비용 0 | 0 | 0 |

M2 수용 기준 ②는 이것으로 닫힌다 — 429의 분류(RATE_LIMITED)·힌트 파싱·AIMD 하향·회복 후 완주가 한 배치 안에서
관측됐다. 승격 경로도 실 quota 없이 반복 관측 가능해졌다(실 모델에서는 REJECTED가 60문장 중 1건이라 하루 한 번 본다).

**단위 검증 (LLM 0회, common +15 / worker +3):** quota 창(분당·일일, 모델별, UTC 자정 리셋)을 시계를 돌려 검증,
503 주입, 시드 재현성, 실제 `PromptAssembler` 출력 파싱, 동명이인 첫 후보, 스트림 청크, **규칙 NER + 인조 KB +
가짜 Translator + QualityGate를 끝까지 통과하면 VERIFIED / 이름을 빠뜨리면 REJECTED**, 그리고 워커의
`FailureClassifier`·`RetryAfterHint`가 가짜 429/503을 실 provider와 같은 분기로 읽는지.

**한계.** quota 창은 프로세스 단위다(api와 worker가 각자 셈) — 워커 단일 인스턴스(D11)라 배치 경로에선 문제가 없다.
토큰 수는 문자 수 × 0.65 추정. `docker compose up -d worker`는 의존 서비스(api)를 기본 env로 재생성하므로 실험
중엔 반드시 `--no-deps` — 이 데모를 준비하다 api가 골든셋 300으로 되돌아가 크기 탐침이 실제 배치를 만들었다
(`83ca0bb5`, 13/61 fake 처리 후 PAUSED — 채점에서 기본 제외되므로 무해, 지워도 된다).

## gemma-4 탐침 — quota가 아니라 출력 형식에서 막혔다 (M4-S2 ①, 2026-09-21)

**목적.** M4-S2 선행 조건 ①: `gemma-4-26b-a4b-it`의 RPD/RPM을 429 `quotaValue`로 실측해 quota 풀의 전체 크기를 안다
(T0의 목적지 후보). 방법은 M3-S5와 동일 — 워커(리미터 20 RPM 출발, 최대 60)로 골든셋 60 배치를 흘려 429 본문을 읽는다.
`eval/probe_model.py --model gemma-4-26b-a4b-it` (생산 프롬프트, 캐시 off, 승격 off). 결과 정본 `eval/probe_gemma-4-26b-a4b-it.json`.

**결과 (25분 상한에서 pause):** 60건 중 **SUCCEEDED 0 / FAILED 12 (전부 PARSE_ERROR) / RUNNING 1 (26분째 응답 없음) / PENDING 47.
429 0건 → RPM·RPD 미실측.**

| 관측 | 값 |
|---|---|
| 응답 12건의 실패 원인 | 전부 `PARSE_ERROR` — `Unexpected character ('*')`: 응답이 JSON이 아니라 **마크다운(`*`)으로 시작**. Structured Output 지시(BeanOutputConverter format)를 따르지 않는다 |
| 토큰 | 입력 평균 788, **출력 평균 64 (0~151)** — 번역문 분량이 아니라 짧은 텍스트·빈 응답 |
| 응답 간격 | 29 / 36 / 47 / **696** / 40 / 28 / 47 / 145 / 127 / 128 / 120초 — 평시 30~50초, 11.6분 정지 1회, 후반 2분대. 25분에 12건 = **0.5 jobs/min** |
| 걸린 호출 | 1건이 26분째 RUNNING — 호출 측 **하드 타임아웃 부재**가 드러남 (M3-S5의 "동기 경로 실패 분류 부재"와 같은 축, 워커 쪽) |

**해석.** quota 탐침이 성립하려면 처리량이 리미터 상한(60 RPM)까지 올라가야 하는데, gemma-4는 응답당 30초~2분이라
20 RPM에도 못 미친다 — **한도에 닿기 전에 지연이 먼저 막는다.** 그리고 닿았어도 결과를 쓸 수 없다: 이 파이프라인은
Structured Output JSON(`translatedText` + `uncertainSpans`)을 계약으로 삼는데 gemma-4는 그것을 지키지 않는다. 즉 gemma-4를
T0 목적지로 쓰려면 **모델별 출력 모드**(평문 응답 + 결정론 추출)라는 설계 항목이 먼저 필요하고, 그 전엔 quota 크기가
의미가 없다. ADR-010 재검토 조건 "gemma-4 등 RPD 실측 시"의 전제가 성립하지 않는다 — **M4 quota 풀은 당분간 500 + 20이다.**

**따라 나온 갭 2건.** ① 워커 LLM 호출에 하드 타임아웃이 없다(26분 RUNNING). ② `FailureClassifier`는 `*`로 시작하는
응답을 PARSE_ERROR로 정확히 분류했고 토큰은 원장에 남았다(12행, 파싱 실패 시에도 과금 회계 유지 — M2 설계대로).

배치 `9a7c0edc`는 PAUSED로 둔다(gemma 결과는 채점에 안 쓰인다).

**갭 ③ — 모델을 바꿔 워커를 재기동하면 pause된 배치의 재시도 메시지가 새 모델로 처리된다.** PARSE_ERROR는 재시도
대상이라 ACK되지 않고 스트림에 남는데(at-least-once, ADR-001), 배치 pause는 펌프의 발행만 멈추지 소비를 막지 않는다.
gemma 탐침 뒤 워커를 flash-lite(v5 프롬프트)로 되돌리자 12건이 재전달돼 4건이 flash-lite로 SUCCEEDED, 나머지는 워커를
세우는 사이 NER_UNAVAILABLE/UNKNOWN으로 실패했다 — 한 배치 안에 두 모델·두 프롬프트가 섞였고 flash-lite 일일 quota
4회를 썼다(499/500). 수습은 수동(pending 9건 XACK+XDEL, 미읽기 2건 XDEL). 근본 대책은 워커가 소비 전에 배치 상태를
확인하거나 job에 모델을 고정하는 것 — M5/M6 항목으로 넘긴다. **모델 교체 재기동 전에는 `XPENDING`이 0인지 볼 것.**

## 인명 정답지 재구성 — KB에서 떼어 국역에 묶기 (2026-10-04, LLM 0회)

위 두 측정(ETS 98.21%, KB A/B 0.9038 → 0.9712)의 정답지 `ner_groundtruth_300.json`을 다시 뜯어봤다. 인명 *위치*는
국편 `idx_person` 어노테이션이라 독립적이지만, 두 가지가 측정을 KB 쪽으로 기울이고 있었다.

1. **한글 표기가 KB 값이다.** `research/06_NER/build_groundtruth.py`의 `korean_name()`은 런타임 KB 역색인의 첫 후보
   (`pids[0]`)를 정답으로 적었다. KB에 있는 이름의 ETS는 "KB대로 썼는가"이고, 성 없는 키가 다른 사람에 링크되면
   정답지도 그 사람을 적는다.
2. **KB 밖 이름이 거의 빠져 있었다.** 국편 페이지를 다시 받으면(`eval/crawl_idx_person.py`) 225문장에 인명 528건인데
   정답지에는 383건만 있다. 빠진 156건 중 **151건이 KB 밖 이름**이다(거른 코드는 레포에 없다). 그래서 정답지의 KB 밖
   비율은 5%였고, 전수 MISS 36.51%와 달랐다(위 품질 게이트 절이 "별도 측정 대상"으로 남긴 바로 그 차이).

**새 정답지 (`eval/name_gold.py` → `eval/name_gold_300.json`).** 어노테이션 원본 전체를 쓰고, 한글 표기는 같은 문장의
**전문가 국역에 실제로 나온 표기**로 붙인다. 후보는 KB 링킹 결과 → person_master 표기 → `hanja` 라이브러리 독음(성
독음은 마스터에서 보정: 沈→심, 첫 글자 두음법칙) 순서로 찾고, 이름은 어절 첫머리 + 뒤에 조사만 오는 자리에서만
인정한다. 한문 판독은 하지 않는다 — 판정은 한글끼리의 비교다.

| 상태 | 건수 | 뜻 |
|---|---|---|
| agree | 343 | KB가 주입할 표기가 국역에 있음 — **KB 표기가 국역으로 검증됨** |
| lib / master / given / rare | 107 / 21 / 9 / 5 | KB 밖 이름의 국역 표기를 라이브러리 독음·마스터·이름부·희귀자(BMP 밖, 국역이 유일한 근거)로 찾음 |
| kb_alt | 5 | 동명이인 후보 중 하나가 국역에 있음 |
| surname_fix | 5 | **성 없는 키의 오링킹** — 珙 → KB 윤공 / 국역 이공(3건), 宗善 조종선 / 유종선, 尙安 이상안 / 김상안 |
| ref_reading / unresolved | 8 / 24 | 국역 표기를 믿을 수 있게 못 찾음 — **채점 제외** (국역 저본이 다른 글자인 경우 李必崇 → 이필영, 한 글자 이름, 칭호) |

- 채점 대상 495 / 527 (93.9%). KB 밖 171건(32.5%) — 전수 MISS율과 맞는다.
- **KB가 확정·주입하는 이름 350건 중 국역과 다른 것 2.0% (7건):** 오링킹 5 + 독음 차이 1(尹爓: KB 윤염 / 라이브러리·국역
  윤섬) + 국역 생략. 오링킹은 검증 게이트를 그대로 통과한다 — 주입한 이름이 번역문에 들어갔으니까.
- 종전 정답지가 *틀리게* 감점하던 사례도 있다: 慶業은 런타임 OFFICE 단계가 임경업(국역과 일치)을 골랐는데
  정답지는 `pids[0]`인 박경업이었다.
- 국편 마크업에는 인물 ID가 없다(`title`이 한자뿐) — 링킹 정확도의 정답(인물 ID)은 이 소스로 만들 수 없다.

### 구간별 재채점 — 병목이 LLM에서 KB 커버리지로 (예비, eval60)

`eval/name_metrics.py` — 새 정답지로 기존 배치를 KB 포함/미포함 구간으로 나눠 채점, 문장 재표집 bootstrap 95% CI.
결과 정본 `eval/name_metrics_eval60_prelim.json`.

| 구간 (이름 수) | LLM 단독 (v0, 3라운드) | 파이프라인 (v4, 3라운드) | Δ [95% CI] |
|---|---|---|---|
| 전체 (130) | 0.869 | 0.923 | +0.054 [+0.012, +0.092] |
| KB 포함 (99) | 0.919 | **0.990** | +0.071 [+0.018, +0.117] |
| **KB 미포함 (31)** | **0.710** | **0.710** | **0.000** |
| 종전 정답지 모집단 (101) | 0.911 | 0.980 | +0.069 — 종전 0.9038 → 0.9712의 재현 |

- 주입은 KB가 덮는 이름에서만 작동하고, 거기서 오류를 8 → 1로 줄인다. KB 밖 이름은 주입 전후가 같다.
- **파이프라인의 남은 오류 10건 중 9건이 KB 밖 이름이다.** 종전 헤드라인(97.1%)은 이 이름들이 정답지에서 빠져 있어서
  나온 값이고, 전체 이름 기준으로는 92.3%다.
- **예비인 이유:** 표본 47문장(정답 이름이 있는 문장). 두 arm의 프롬프트가 다르다 — v0 KB 런은 다른 머신에서 돌아 이
  DB에 없어서 v4 KB 런을 썼다. KB 포함 구간의 Δ에는 프롬프트 차이가 섞일 수 있다(프롬프트 ablation에서 ETS는 v0~v5
  모두 같았으므로 크지는 않을 것). 같은 프롬프트로 eval300 재측정이 다음 단계다.

### 사전 등록 — KB 주입 A/B 재측정 (2026-10-04, 실행 전 고정)

위 예비 결과(eval60, 두 arm의 프롬프트가 다름)를 같은 조건으로 다시 잰다. 아래는 **결과를 보기 전에** 고정한 것이고,
결과를 본 뒤 바꾸지 않는다. 드라이버 `eval/name_ablation.py`가 이 규칙을 코드로 집행한다.

**조건**
- 표본: `eval300_1925.json` 300문장 − 행 밀림 2문장(`eval/eval_exclusions.json`) = 298문장. 채점 이름 493
  (KB 포함 354 / KB 미포함 139), 채점 제외 28(unresolved·ref_reading).
- 두 arm 모두 새로 돌린다: `kb`(KB_MODE=file) / `nokb`(KB_MODE=noop). 프롬프트 현 생산 `translate-main.st`
  (`main-4a1cb192`, v4), 모델 `gemini-3.1-flash-lite`, temperature 0.2, 캐시 L1·L2 off, 승격 off, 라우팅 off.
- 3라운드, **교차 순서** r1 kb→nokb, r2 nokb→kb, r3 kb→nokb — 측정 기간 중 provider 변동이 한 arm에 몰리지 않게.
- self-check(prompt_version·kb_version·model_used)가 어긋난 배치는 버리고 같은 자리를 다시 돈다. 문장이 5% 넘게 빠진
  (FAILED) 라운드도 다시 돈다. 라운드는 이 3개뿐이다 — 결과를 보고 라운드를 늘리지 않는다.
- 채점 입력은 실행 전에 고정한다 (드라이버가 상태 파일에 해시를 기록하고 `--report`에서 대조):

| 파일 | sha256 (앞 12자) |
|---|---|
| `eval/name_gold_300.json` | `e7d238b08ff2` |
| `eval/eval_exclusions.json` | `2d84a8a9b4fc` |
| `eval/idx_person_300.json` (정답지의 원자료) | `d4ef0bd3fb72` |

**지표** — 이름은 라운드 평균 적중의 micro 정확도, CI는 문장 재표집 paired bootstrap 95%(2,000회). chrF는 라운드
중앙값의 corpus chrF, paired bootstrap 1,000회. CI는 문장 표집의 불확실성만 담는다(라운드는 평균으로 흡수).
- 주 지표: KB 포함 이름 정확도 Δ(kb − nokb), KB 미포함 이름 정확도 Δ
- 보조: chrF Δ / 함께 보고: 채점 제외를 오답으로 친 하한, relinked·wrong_injected, eval60 대 나머지 240 분리
  (eval60은 v4 프롬프트를 고른 표본이다)

**판정 규칙**
| | 규칙 | 통과 시 주장 |
|---|---|---|
| H1 | KB 포함 Δ의 95% CI 하한 > 0 | KB 주입은 KB가 덮는 이름의 정확도를 올린다 |
| H2 | KB 미포함 Δ의 95% CI가 0을 포함 | KB 밖 이름에는 효과가 없다 (기대) |
| H3 | chrF Δ의 95% CI 하한 > −2.0 (§5.4 비열등 마진) | 주입이 문장 품질을 떨어뜨리지 않는다 |
| H4 | kb arm 인명 오류 중 KB 밖 이름의 몫 ≥ 0.5 | 남은 오류의 병목은 LLM이 아니라 KB 커버리지다 |

H1이 실패하면 헤드라인("KB 주입으로 인명 정확도 향상")을 내린다. H4는 기술 통계라 CI 없이 점추정으로 판정한다.

**검정력 (사전 추정)** KB 미포함 139명이면 정확도 95% CI 반폭이 약 ±7~8%p다. H2는 이 폭 안의 효과를 "없음"으로 읽는
셈이므로, 보고할 때 "±8%p보다 큰 효과는 없다"로 쓴다.

**이후 단계에 미리 걸어 두는 설계 제약** (실행 전에 정해 둔다)
- Step 4 동적 few-shot: 현 고정 예시 5개는 **원문 없이 국역문만**이고 18세기 기사다. 검색 기반 예시는 원문+국역
  쌍이 되므로, "고정 5개를 원문+국역 쌍으로" 조건을 따로 두어 형식 효과와 선택 효과를 가른다. 검색 인덱스는
  `eval/leakage.py` 규칙 1·2·4(평가 문장·같은 날짜 3,695행·밀림 의심 행 제외)를 통과한 행만 쓴다. 5개 조건은
  LLM 없이 먼저 거르고, LLM 비교는 미리 정한 한 쌍만 한다. eval60과 나머지 240을 따로 낸다.
- Step 5 오프라인 KB 확장: 마이닝 입력은 규칙 1·2·4를 통과한 행, 주장은 **시기 분할**(재위 1–20년에서 캐고
  21–27년 평가 문장 72개로 평가)로 잰다. KB 미포함 이름이 72문장으로는 적으므로, 국편 어노테이션을 더 받아 KB 밖
  이름 중심 평가셋을 늘린 뒤에 판정한다(전문가 불필요, 비용은 LLM 호출뿐).
- 라이브러리 독음을 주입하는 조건은 넣지 않는다 — 정답지가 라이브러리 독음 후보로 찾은 것이라 그 조건에 유리하다.

## 오프라인 KB 확장 — 국역에서 KB 밖 이름의 표기 캐기 (Step 5, 2026-10-05, LLM 0회)

KB 밖 이름의 87%는 person_master에도 없어서 KB 범위를 넓혀서는 덮이지 않는다(위 절). 남은 출처는 병렬 코퍼스의
**전문가 국역**이다. CRAG의 "검색 결과 평가 → 교정 행동"을 런타임 외부 검색이 아니라 KB 구축 단계로 옮겼다 —
**CRAG-inspired offline KB expansion**이지 CRAG 구현은 아니다. 역사 인명은 잘못 들어가면 이후 번역 전체로 오류가
퍼지므로 실시간 보강보다 "자동 발견 → 후보 → 등급 → 승격"이 맞다고 봤다.

**방법 (`eval/kb_mining.py`).** 코퍼스 전수 NER(`eval/ner_corpus_cache.py`, 고유 원문 52,764건, 99분)의 PER 멘션
중 KB 링킹이 MISS인 것(2자 이상)을 행마다 같은 행 국역에 대 본다.
- 투표: **exact** — `hanja` 라이브러리 독음(성 보정·두음)이 국역의 이름 자리(어절 첫머리 + 조사)에 있다 /
  **aligned** — 독음 후보가 없고(희귀자·관행 독음) 같은 행의 다른 이름을 뺀 뒤 성·길이가 같은 토큰이 하나만 남는다.
- 등급(결과 전에 고정): **High** 투표 ≥ 2·합의율 ≥ 0.8·(exact ≥ 1 또는 투표 ≥ 3) → 자동 승격 / **Medium** 투표 ≥ 1·
  합의율 ≥ 0.6 → 검수 대기열(전문가 부재로 승격 안 함) / **Low** → Unknown.
- 일반 낱말 필터(개발 실행 후 추가, 등급 기준은 그대로): aligned로만 모인 표기가 국역에서 멘션보다 훨씬 자주
  나오면(> max(5 × 멘션 행, 20)) Low — 李進 → "이와", 夏衍 → "하니" 같은 것을 막는다. 전 연차에서 369키를 내렸다.
- 누출 방지(`eval/leakage.py`): 평가 문장·같은 날짜 3,695행·밀림 의심 3,757행을 입력에서 뺀다 → 55,149행.

**결과**

| | 전 연차 (평가 문장·날짜 제외) | 시기 분할 (1–20년에서 캐고 21–27년 평가) |
|---|---|---|
| KB 밖 표기 키 | 12,057 | 9,584 |
| High / Medium / Low | **4,028** / 5,694 / 2,335 | 3,035 / 4,630 / 1,919 |
| A. 유사-OOV 정밀도 High (Medium) | **97.4%** (82.3%) — 1,461키 | 97.3% (83.8%) — 1,266키 |
| B. 골든셋 KB 밖 이름 중 High가 덮는 비율 | **62.6%** (87/139, 전부 정답) | **25.0%** (9/36, 전부 정답) |
| C/D. 코퍼스 KB 밖 멘션 중 High가 덮는 비율 | 67.3% (학습 행 안 — 표본 내) | **33.0%** (시험 연차 8,079멘션, Medium 포함 43.3%) |

- **정밀도는 유사-OOV 97%를 대표값으로 본다.** KB에 있는 이름을 KB 없이 같은 방법으로 캐서 국편 KB 표기와 대조한
  값이다. 골든셋 100%와 시험 행 국역 대비 99.7%는 정답지·대조 표기도 라이브러리 독음 경로로 찾은 것이라 낙관적이다.
- **커버리지는 시기 분할이 진짜 크기다.** 같은 인조 연간 안에서 날짜만 빼면 같은 인물이 다른 날 계속 나와 62.6%로
  보이지만, 새 시기로 옮기면 25~33%다. "번역된 구간에서 배운 이름을 미번역 구간에 쓴다"는 주장은 이 숫자로 해야
  한다 — 미번역 구간은 다른 왕대라 인물 겹침이 더 적을 수 있고, 그쪽은 아직 재지 않았다.
- aligned로만 승격된 48키는 라이브러리 독음과 다른 국역 관행을 잡은 것이다: 申櫄 → 신훈(라이브러리 신춘),
  李汝恬 → 이여염(이름 안 두음), 任賚之 → 임뇌지. 朴昊 → 박민처럼 국역 저본의 글자가 다른 듯한 것도 섞인다 —
  목표가 "국역이 쓰는 표기"라서 그대로 둔다.
- 희귀자(BMP 밖) 이름(골든셋 rare 5건)은 하나도 High가 되지 않았다 — NER이 그 글자를 멘션으로 잘 못 잡거나
  출현이 1회뿐이다. 남은 공백이다.

**산출물.** `kb/{inverted_index,id_lookup}_injo_aug.json`(전 연차, 기존 2,690명 + High 4,028 = 6,718명 · 13,431키)과
`_injo_aug_y01-20`(시기 분할 평가용). 항목에는 `출처: corpus_mining`·투표 수·합의율이 붙고 관직·활동기간은 비어
있다(링커의 활동기간 필터는 0으로 통과, 프롬프트에는 관직 없이 들어간다). Java 워커가 재빌드 없이 읽는다 —
`KB_DIR=/kb-local KB_NAME=injo_aug`(compose가 레포 `kb/`를 `/kb-local`에 읽기 전용으로 마운트), 로드 확인
`injo_aug-021c2976`. 검수 대기열은 `eval/kb_mining_all_review.tsv`(Medium 우선 정렬).

**아직 모르는 것.** 확장 KB가 번역의 인명 정확도를 실제로 올리는지는 LLM 런이 필요하다 — 시기 분할 KB
(`injo_aug_y01-20`)로 21–27년 문장을 kb 대 kb_aug로 비교하는 것이 다음 측정이고, 사전 등록에 적은 대로 KB 밖 이름이
적어(36명) 국편 어노테이션을 더 받아 평가셋을 늘린 뒤에 판정한다.

### 배포 전 검증에서 잡은 결함

`FailureClassifier`가 상태 코드를 `contains("500")`으로 찾아, **타임아웃 값 자체의 숫자**에 걸렸다.

|---|---|

회귀 테스트 2건을 추가했다. 수정 후 5000ms에서 504, 5.24초에 절단 확인.
